# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A **greenfield, spec-driven ERP** (product name **Nainer**, DB `niner_db`) for small retailers that sell both in a physical store and across 2–5 online marketplaces (Mercado Livre, Shopee, Amazon, own e-commerce). The product's job is to make the ERP the single source of truth for stock and price, and to keep every channel in sync automatically (zero overselling).

**As of spec v2.0 it is a multi-tenant SaaS**, sold by subscription. Two planes that must never be conflated:
- **Control Plane ("Plataforma Nainer")** — Vetor's business: tenants, pricing plans, subscriptions, invoices, billing, support. Global tables under module `plataforma/` (outside tenant RLS).
- **Tenant Plane (the retailer's ERP)** — catalog, stock, orders, channels and the retailer's own internal finance (legacy `financeiro`, scope Q5). Every row isolated by `id_tenant`.
- Vocabulary rule: *assinatura/plano/trial/mensalidade/gateway* = **platform** (Vetor charges the retailer); *caixa/crediário/contas a pagar-receber/conta corrente da loja* = **retailer's finance**. Never mix.

Acquisition is self-service via a **public site** with a **60-day, no-card trial**; a **backoffice** manages tenants; billing charges subscribers (gateway **to be defined** — modelled behind an abstract adapter, manual billing at first).

## Working model: spec-driven

Nothing is implemented without the preceding artifact being approved, in this chain:
**Constitution → Product spec (PRD) → Technical plan → Tasks.** Golden rule: *if a question arises during implementation, the answer must be in the spec; if it isn't, update the spec before writing code.*

For any new feature use the templates in the spec: **§5 Feature Spec**, **§6 ADR**, **§7 Task**. Acceptance criteria are written as `Dado/Quando/Então` (Given/When/Then) and each becomes an automated test **before** merge.

## Constitution — non-negotiable principles (spec §1)

These override any convenience; do not violate them without a superseding ADR:

- **P1 — Stock is the source of truth.** The ERP is master of stock and price; marketplaces are replicas. No integration writes stock back without going through the central domain.
- **P2 — Every integration is async and idempotent.** Marketplace calls go through the outbox/queue with retry. Reprocessing an event must never duplicate an order, stock movement, or invoice.
- **P3 — Auditability.** Every mutation of stock/price/order writes an immutable record (who, when, source, old/new value).
- **P4 — API-first.** The React frontend consumes only the REST API. **No business logic in the frontend.**
- **P5 — Tests track the spec.** Every acceptance criterion becomes an automated test before merge.
- **P6 — Simplicity first.** Modular monolith before microservices; one Postgres instance; no external broker (Kafka/RabbitMQ) in v1 — use Postgres as the queue via outbox + `SELECT … FOR UPDATE SKIP LOCKED`.
- **P7 — Money in `NUMERIC`.** Never float for monetary values — `NUMERIC(12,2)` in the DB, `BigDecimal` in Java. **Note:** the legacy `db/` schema uses `FLOAT` for money; do not carry that forward.
- **P8 — Tenant isolation is inviolable.** No query crosses a tenant boundary; enforced by the DB via Postgres RLS (`FORCE ROW LEVEL SECURITY`), not just app code. App role `niner_app` never has `BYPASSRLS`; migrations run as `niner_owner`. Every tenant-data table carries `id_tenant` + an RLS policy; `plataforma/` tables are the documented exception. Every non-request path (worker/outbox/webhook) sets the `TenantContext` before touching domain data.
- **P9 — Plane separation (control-plane × tenant).** Platform data (subscription, invoices, billing) and retailer data never share an access policy. Platform staff reach tenant data only via **audited impersonation** (P3).

## Intended architecture (spec §3)

Modular monolith, **one API with three surfaces** (ADR-007): `/api/publico/**` (public site: signup, checkout, trial), `/api/v1/**` (tenant ERP, JWT `tid` claim + RLS), `/api/admin/**` (platform backoffice, staff JWT). Planned stack: **Java 25 + Spring Boot 4.x**, **PostgreSQL 18** (Docker, DB `niner_db`), **React 19 + Vite + TypeScript**, Flyway migrations, JWT auth (tenant roles `ADMIN`/`OPERADOR`; staff roles `SUPER_ADMIN`/`SUPORTE`/`FINANCEIRO`). Tests: JUnit 5, Testcontainers (real Postgres), WireMock (marketplace APIs), Playwright (critical e2e). **springdoc-openapi is in the spec but was never implemented** (checked 2026-08-14: no `springdoc-*` dependency in `api/pom.xml`, no `@Operation`/`@ApiResponse`/`@Tag` anywhere in `api/src/main`) — there is **no generated OpenAPI document**; the real API contract lives in the "Contrato de API" sections of `docs/telas/*.md`, written before the code. Adopting springdoc is future work. Virtual threads enabled for integration I/O. **API is stateless**; the three React apps read the API base-URL at **runtime** (not baked into the bundle) so two API servers can run behind a switchable address for maintenance/failover.

**Tenant isolation (ADR-006):** shared DB + `id_tenant` discriminator on every domain table + Postgres RLS. `tenant 1:N empresa` (1:1 in v1). Request resolves tenant from JWT `tid` → `TenantContext` → `SET LOCAL app.id_tenant` per transaction; policies use `current_setting('app.id_tenant')`. Closes legacy Q6: keep `id_empresa` **and** add `id_tenant`.

Domain modules (packages): `catalogo/ estoque/ pedidos/ precos/ canais/ identidade/ integracao/{mercadolivre,shopee}` (+ `financeiro/` if Q5), plus the control-plane module **`plataforma/`** (tenant, plano, assinatura, fatura, pagamento, uso_tenant, staff — global, no tenant RLS). Modules communicate via Java interfaces + internal domain events.

Key patterns:
- **Adapter / anti-corruption layer per marketplace**, all implementing a common `CanalDeVenda` interface (`publicarAnuncio`, `atualizarEstoque`, `atualizarPreco`, `importarPedidos`, `confirmarEnvio`). The domain never sees ML/Shopee payloads. Adding a second channel (Shopee, §Fase 3) is the test of this design.
- **Outbox pattern:** stock/price mutations write an event to `outbox_eventos` in the same transaction; a `@Scheduled` worker publishes to channels with exponential backoff + dead-letter.
- **Idempotency:** imported orders keyed by natural key `(canal, id_externo)` with a unique constraint; processed webhooks record their `webhook_id`.

The new core data model, API contract sample, and docker-compose layout live in spec §3.3–§3.5 (migration sequence V001–V095 in §3.5.1; control-plane tables in §3.3.11). The repo layout is `api/` (Spring Boot) + three React apps — `web/` (retailer ERP), `admin/` (platform backoffice, **exists** — React, port 5174), `site/` (public acquisition).

## Build / run

Per spec §3.5: `docker compose up -d db && docker compose run --rm flyway` brings up Postgres and applies `db/migration/`; `docker compose up -d --build api` (or `cd api && ./mvnw spring-boot:run`) for the API (port 8080, connects as `niner_app`); `cd web && npm run dev` (5173) and `cd site && npm run dev` (5175) for the fronts. API tests: `cd api && ./mvnw test` (Testcontainers — see `api/README.md` for the container-runtime workaround when no JDK is installed on the host). `cd admin && npm run dev` (5174) para o backoffice da Vetor — ele **existe** e tem build próprio (`tsc -b && vite build`).

**Fotos de produto em dev exigem o emulador de object storage** (ADR-013) — sem ele, upload/exclusão de imagem falha em runtime, não na subida: `docker compose up -d fake-gcs` (porta 4443, volume próprio, as imagens sobrevivem a restart). Rodando a API **pelo compose**, o `.env` já aponta certo (`NINER_STORAGE_HOST=http://fake-gcs:4443` para a API, `NINER_STORAGE_BASE_URL=http://localhost:4443` para o navegador — só a porta publicada é resolvível fora do Docker). Rodando a API **no host** (`./mvnw spring-boot:run`), sobrescreva `NINER_STORAGE_HOST=http://localhost:4443` (PowerShell: `$env:NINER_STORAGE_HOST='http://localhost:4443'`). Host vazio = GCS real, que exige credencial. Detalhes: `docs/infra/armazenamento-imagens.md` §3 (Opção C).

A etiqueta calibrada volta por script, não à mão (2026-08-24):** `db/scripts/seed_etiqueta_calibrada.sql` recria o modelo de etiqueta já acertado na Argox OS-2140 física (rolo 110mm, 3 colunas, 34 × 31,7mm, espaçamentos 3,00/2,50/2,20 e os 4 campos posicionados). Esses números são resultado de **duas sessões de calibragem com etiqueta impressa a cada rodada** — não se redigitam de memória. Rode depois do signup recriar o tenant: `docker exec -i niner-db psql -U niner_owner -d niner_db < db/scripts/seed_etiqueta_calibrada.sql` (idempotente; resolve o `id_tenant` pelo slug e **seta `app.id_tenant`**, sem o que o `FORCE RLS` barra o INSERT e esconde o SELECT). ⛔ **Não promova a migration:** é dado de um tenant e vai mudar enquanto a calibragem evoluir — migration aplicada não pode ser editada (quebra o checksum do Flyway) e rodaria em produção.

**Arquivo privado (XML fiscal, dado pessoal) usa outro storage** (ADR-014): `docker compose up -d minio minio-init` — MinIO na 9300 (API S3) e 9301 (console). Rodando a API no host **não precisa exportar nada** (o default já é `http://localhost:9300`); pelo compose, o serviço `api` já recebe `http://minio:9000`. Sem o MinIO no ar a API sobe igual — a falha vira 503 na primeira gravação. Detalhes: `docs/infra/armazenamento-privado-minio.md`.

⚠️ **Type-check do front é `cd web && npx tsc -b` — nunca `tsc --noEmit`.** O `web/tsconfig.json` é *solution-style* (`"files": []` + `references`), então `--noEmit` ignora as referências, **checa zero arquivos e sempre passa**. Isso já mascarou 19 erros reais acumulados no repositório (descoberto em 2026-08-14). `npm run build` = `tsc -b && vite build`; se o build falhar depois do type-check, o problema é do bundler, não de tipos.

## Conventions to honor when building

- API: version in path (`/api/v1/...`); errors as Problem Details (RFC 9457); list endpoints paginate by page number (`pagina`/`limite`, `LIMIT/OFFSET` + total count) — not cursor, so screens can jump to any page (revised 2026-07-21, see `docs/PROGRESSO.md`); OpenAPI written **before** implementation (the contract is part of the feature spec).
- Flyway migrations under `db/migration`, versioned and reversible.
- Channel credentials encrypted at rest (AES-GCM, key outside the DB); `JSONB` for raw integration payloads.
- Everything (identifiers, table/column names, domain language) is in **Portuguese** — match the existing vocabulary (`produto`, `variacao`, `estoque`, `movimentacao_estoque`, `canal`, `anuncio`, `pedido`).
- **Impressão em bobina térmica (80mm)** — papeleta de venda, comprovante de crediário e vale-mercadoria saem na mesma impressora, e a calibragem que funciona está em `docs/telas/papeleta-venda.md`: largura da **área imprimível** (75mm, não os 80mm do papel — declarar mais faz o driver encolher tudo), `left: 0` (a origem do CSS já é a área imprimível), **42 colunas**, Consolas **em negrito** (térmica é 1 bit: haste fina sai "falhada") e `print-color-adjust: exact`. Documento que não couber em 42 colunas precisa ser reorganizado (ex.: item em 2 linhas), não espremido na largura. **Nada disso aparece na tela, no PDF ou em teste automatizado — só imprimindo.**
- **⚠️ Método de repositório que roda FORA de uma transação vê `tenant_atual()` como NULL — e falha de dois jeitos, um deles em silêncio (2026-08-21, auditoria):** sem `@Transactional`, o `TenantAwareTransactionManager` nunca executa o `SET LOCAL app.id_tenant`. Num **INSERT** isso estoura (coluna `NOT NULL`) e o handler global traduz para *"Registro em uso por outro cadastro"* — mensagem sobre exclusão de cadastro para uma emissão de nota. Num **SELECT** é pior: o filtro casa zero linhas e o método devolve `Optional.empty()`, que costuma significar "não existe, pode seguir" — foi assim que o cancelamento da devolução ao fornecedor **devolveu o estoque sem enviar o evento 110111 à SEFAZ**, deixando uma NF-e 55 autorizada contra uma saída que não aconteceu, com resposta 200. ⚠️ Ao copiar um método de repositório, **a anotação é parte do que se copia**: os dois casos tinham uma irmã anotada logo acima. E cuidado com o falso conforto da suíte: o caminho fiscal da devolução **não tem teste** (a suíte roda com `emite_nfe = false`), então os dois defeitos passaram por 911 testes verdes.
- **⚠️ Auditoria de código: peça o DESCARTE junto com o achado (2026-08-21).** Seis rodadas de dois agentes renderam 31 correções, e o que mais economizou tempo foi o que eles **provaram não existir**: um previu que o bug do `putIfAbsent` teria um irmão na devolução ao fornecedor, foi lá e mostrou que a alocação ali é FIFO por `numero_item`, com teto e recusa de sobra — fechando a suspeita em vez de deixá-la aberta. Outro delimitou a superfície de staff a **um único ponto** em vez de deixar o módulo inteiro sob suspeita. Peça também que digam **o que ficou sem cobrir** e que **pulem área improdutiva** dizendo por quê (correção criptográfica e XSD não se verificam lendo, se verificam executando) — relatório honesto vale mais que relatório cheio. E **confira cada achado no código antes de corrigir**: alguns caem na conferência.
- **⚠️ "Duas linhas do mesmo produto na mesma venda" virou NORMAL — reveja todo `GROUP BY id_variacao` (2026-08-22):** o preço congelado do orçamento tornou comum o que o código tratava como "raro, mas possível". A **Devolução de Produtos** agrupava por `id_variacao` e derivava o unitário como **média ponderada**: devolver 1 peça de uma venda 1×R$ 50 + 1×R$ 120 gerava vale de **R$ 85**, valor que a venda nunca praticou — e o mesmo R$ 85 ia para a **NF-e 55**, divergindo de todo item da NFC-e original. Hoje a chave de linha é **(variação, preço)** no back (`chaveLinha`) e no front (`ItemLinha.daVenda` + `chaveLinha`), o saldo é por linha, e a grid avisa qual linha é qual quando há ambiguidade. ⚠️ **A chave de mapa é TEXTO, não `BigDecimal`**: `equals` de `BigDecimal` leva a escala em conta, então `80.00` e `80.0` — que o driver pode devolver de consultas diferentes — seriam chaves distintas e o saldo não casaria. ⚠️ E o preço no request é **opcional**, conferido contra as linhas reais da venda: obrigatório quebraria a devolução sem venda de origem, e aceito sem conferir deixaria o cliente da API escolher o valor do próprio vale. Ver `docs/telas/devolucao-produtos.md`.
- **⚠️ `cfg_tela_campo` tem DUAS dimensões, e "obrigatório" não é a que tira o campo da tela (2026-08-22):** `visivel` decide se o campo aparece; `obrigatorio` decide se ele é exigido — com CHECK garantindo que obrigatório implica visível. Quem quer **enxugar o cadastro** usa `visivel = false`; marcar como não-obrigatório apenas deixa de exigir. ⚠️ E a revalidação no servidor só existia para `String`: todo campo configurável que é **número ou data** ficava sem checagem, por construção (`limiteCredito`, `percComissao`, `pesoBruto`, `pesoLiquido`, `precoOferta`, `dataInicioOferta`, `dataFinalOferta`) — apesar da promessa escrita de que a bandeira vale "de novo no servidor". `exigirSeObrigatorioValor` cobre isso agora. ⚠️ **Ausente é `null`; zero é valor legítimo** (decisão do dono do produto): um cliente sem crédito tem limite R$ 0,00, e o front manda `desmascararMoeda('')` = 0.
- **⚠️ Documento A4 com `position: absolute` imprime UMA página e descarta o resto, em silêncio (2026-08-22):** absoluto é certo para documento de uma página — e é exatamente o que impede paginar. Orçamento com ~30 itens saía sem total e sem assinatura, e **nada na tela, no PDF ou em teste mostrava isso**. O remédio é o mesmo que fez a etiqueta paginar, e vence as duas regras que escondem trabalho sem avisar: `overflow: hidden` do shell (`html, body, #root`) **corta** em vez de paginar, e `visibility: hidden` do isolamento global esconde o pixel mas **mantém o espaço** — trocar por `display: none` nos irmãos. Use `imprimirDocumentoA4()` (`web/src/lib/impressaoDocumento.ts`) + classe `.documento-a4-imprimir`; a classe entra no `<html>` **e** no `<body>`, senão apaga o `#root` de toda impressão do produto. Cabeçalho **só na primeira página** (decisão do dono). ⚠️ **Só se confirma imprimindo** — a correção de 2026-08-22 não foi testada no papel.
- **⚠️ `@page` nomeado sem um seletor que o AMARRE não faz nada (2026-08-22):** o `@page orcamento-bobina` era injetado e nenhuma regra tinha `page: orcamento-bobina`. Saía certo **por acaso**, caindo no `@page` global do projeto (que também é 80mm) — e quebraria no dia em que esse global mudasse, sem nada apontar para a causa. Quem injeta o `@page` injeta junto o seletor.
- **⚠️ Job que retoma trabalho interrompido NUNCA reenvia cego, e não decide o que não sabe (2026-08-22):** o dreno de contingência marcava `TRANSMITINDO` antes de enviar e filtrava só `CONTINGENCIA`/`ASSINADO` — uma falha de rede fazia a nota **sumir da fila para sempre**, com o prazo legal de 24 h correndo e o cupom na mão do consumidor. Ao trazer o estado de volta, duas regras: (a) **carência** antes de reconsiderar (10 min), senão o job atropela a tentativa em curso; (b) **consulta a chave antes de reenviar** (F5) e aplica só o desfecho inequívoco — autorizada grava, `cStat 217` libera o reenvio, **qualquer outra resposta registra e para**, deixando para o humano. Job automático adivinhando desfecho de documento fiscal é pior que job que para.
- **⚠️ Rotina que espelha tributação de terceiro precisa conferir o CRT de quem EMITE (2026-08-22):** a devolução ao fornecedor copia `cst_icms` de `entrada_nfe_item` — o que **o fornecedor** declarou — mas o `<emit>` leva o CRT da **nossa** loja, que por DF37 é 1, 2 ou 4. Uma loja do Simples devolvendo compra do Lucro Real emitia `<CRT>1</CRT>` com `<ICMS00>` destacando ICMS próprio: na melhor hipótese a SEFAZ rejeita, na pior **autoriza** e a loja destaca imposto que não apura. Hoje a montagem **recusa** quando `crt != 2` e o item traz CST. ⚠️ Recusar é o mínimo seguro — a conversão para CSOSN é **regra tributária** e espera o contador.
- **⚠️ Preço congelado de orçamento vale por LINHA, não por variação (2026-08-21):** `ItemVendaRequest.doOrcamento` marca quais linhas da venda o orçamento cobre. O mesmo produto pode aparecer duas vezes na mesma venda — o que o cliente orçou (preço congelado, que a loja **honra**) e as unidades a mais que ele resolveu levar na hora (preço de hoje, que ele não orçou). Antes o preço congelado era mapeado por `idVariacao` e aplicado às duas, e a validação "não pode levar mais do que foi orçado" **somava as duas linhas e recusava a venda inteira**. No front, `ItemLedger.idLinha` é a chave da linha (o SKU não serve mais: duas linhas do mesmo produto) e `dividirParaEnvio` quebra uma linha da tela em dois itens quando o preço não mudou. ⚠️ **Guarda de contrato:** mandar `idOrcamento` sem nenhuma linha marcada é **recusado** — sem ela a venda sairia inteira a preço de cadastro, o orçamento seria consumido e nada indicaria que a loja deixou de honrar o preço prometido. Ver `docs/telas/pdv.md`.
- **⚠️ O papel configurado no DRIVER tem de ser ≥ a página declarada no `@page` (2026-08-21, custou duas sessões na etiqueta):** quando é menor, o navegador **encolhe a página inteira** para caber — e encolher a página encolhe o **passo entre colunas/fileiras**, enquanto o adesivo não encolhe. O erro **cresce a cada coluna** e imita perfeitamente medida errada no cadastro; `Escala: 100%` no Chrome **não corrige**, porque quem escala é o driver. Sintomas que separam as causas: erro que *cresce* é escala ou passo, deslocamento *constante* é margem, e **erro já na PRIMEIRA fileira não é erro de passo** (passo só se manifesta acumulado — erro na primeira aponta para a origem, isto é, o driver). ⚠️ Antes de acusar o hardware, **confira o tamanho do papel no driver**: eu concluí que o cabeçote da Argox só alcançava 102mm e que 3 colunas eram impossíveis; era o preset de 4" do driver, e o `.rtm` do sistema legado (que imprime as 3 na mesma impressora) provou o contrário declarando papel de 110mm. Detalhes: `docs/telas/configuracao-etiqueta.md`.
- **⚠️ Código de barras precisa de ZONA DE SILÊNCIO, e sem ela o leitor RECUSA (2026-08-21):** o branco antes e depois do símbolo — **11 módulos à esquerda, 7 à direita** no EAN-13 (GS1 General Specifications) — não é margem estética: **é por ele que o leitor sabe onde o símbolo começa e termina**. Um código impresso com precisão perfeita e sem zona de silêncio simplesmente não lê. Foi o que o `margin: 0` do jsbarcode causou aqui, posto para o desenho "não desperdiçar espaço" da caixa. Regra: a caixa acomoda **113 módulos** (95 + 11 + 7), não 95 — o módulo se deriva de 113 e as margens vão em `marginLeft`/`marginRight`. Confira também o **tamanho do módulo** (mínimo 80% do nominal de 0,33 mm) e não deixe nenhum campo escuro encostar no símbolo. ⛔ E **nunca** use `shape-rendering: crispEdges` em código de barras: ele arredonda cada borda para a grade de pixels e engrossa umas barras comendo os espaços vizinhos — tentado e revertido no mesmo dia, com etiqueta impressa provando. Ver `docs/telas/configuracao-etiqueta.md`.
- **⚠️ Altura do `@page` da etiqueta é a do ADESIVO, nunca o passo do rolo — e o papel do DRIVER controla o AVANÇO (2026-08-24):** somávamos o espaçamento entre fileiras à página (`59 + 2,2`), e a etiqueta alta saía **partida em duas tiras**. Errado por um motivo físico: a impressora imprime o bitmap e **depois avança até o próximo gap** — quem produz o branco entre fileiras é o avanço, não o desenho. Os dois relatórios do sistema Delphi que imprimem certo na mesma Argox provam (`PrinterSetup.mmPaperHeight` = **30** para adesivo de 30, **60** para adesivo de 60). Hoje: `alturaPaginaImpressaoMm()` = altura da etiqueta; `passoVertical()` está marcada como **não** sendo a altura da página; `FOLGA_PAGINACAO_MM` (0,2 mm) tira o bloco de encostar na página, senão um sub-pixel nasce **uma página em branco entre cada etiqueta**. ⚠️ **Por que o modelo de 31,7 funcionava com a conta errada:** o papel do driver (31 mm) **cortava** a página de 33,9, sobrando por acaso ≈ o adesivo — o erro viveu escondido desde 2026-08-21, e só apareceu quando o papel subiu. ⛔ **E o papel do driver não é só área de desenho, é AVANÇO:** papel 60 com página 31,7 faz a impressora **pular uma etiqueta em branco**. Não existe valor único que sirva a dois rolos; o papel tem de casar com o rolo. O Delphi escapa porque grava o tamanho no relatório e o aplica por trabalho via DEVMODE — **web não tem essa API** (`@page size` é dica, quem escolhe é o driver), e formulários do Windows não servem: o driver Seagull expõe só os 4 tamanhos próprios. ⏭️ A saída definitiva seria um **agente local de impressão** (decisão de produto pendente). ⚠️ Ao medir a foto impressa, **linha impressa × picote físico** separam erro de passo de erro de origem: dois limiares no mesmo perfil horizontal (preto sólido = nosso desenho, queda leve = vinco do papel). E o `.rtm` do legado é evidência sobre o **comportamento**, não sobre a geometria do rolo que está na impressora agora — copiei a margem dele e fiz a 1ª coluna começar fora do papel.
- **⚠️ Restrição do banco costuma ter uma IRMÃ em Java — e ela só aparece testando pela API (2026-08-24):** ao liberar campo repetido na etiqueta (V060, etiqueta destacável), a `UNIQUE (id_config_etiqueta, campo)` era só metade: `EtiquetaConfigService.validar` recusava com *"Campo repetido na etiqueta: X"*, e essa validação **não aparece lendo o schema**. Quem a revelou foi um `POST` de teste respondendo **400** — conferindo só pela tela, o editor deixaria montar o layout inteiro e a falha apareceria no **Salvar**, com o trabalho já feito. Regra: ao remover uma restrição do banco, `grep` pela mensagem de erro no `api/src/main` atrás da irmã, e valide pela **API**, não pela tela. ⚠️ E procure também o **teste** que prendia o comportamento antigo (aqui, `campoRepetidoEhRejeitado`) — ele reprova o build e, mais importante, precisa ser **invertido** para prender o novo comportamento (P5), não apagado.
- **⚠️ Leitor recusando código de barras impresso? MEÇA a etiqueta antes de mexer no desenho (2026-08-24, fechou uma pendência que resistiu a 3 correções):** o EAN-13 saía com a geometria **correta** e mesmo assim não lia. Três rodadas mexeram no SVG e nenhuma podia funcionar. A causa apareceu medindo a saída — perfil de intensidade extraído da foto (`ffmpeg` recorta + `format=gray` + média vertical de 60 linhas, runs de preto/branco lidos em Node): das **59** transições de um EAN-13 sobravam **31**, e a barra mais fina tinha **2,25 módulos** em vez de 1,0. ⭐ **A medida que fechou o diagnóstico foi a que deu CERTO:** a largura total do símbolo batia com o previsto (≈26 mm × 25,2 mm) — se a geometria estivesse errada ela acusaria, então o erro só podia estar na **repartição entre preto e branco**. Cada barra engordou ~0,33 mm e cada espaço encolheu o mesmo: *bar width growth*, assinatura de **intensidade (temperatura) alta demais** na térmica. Segundo sintoma de graça na mesma foto: o texto **vazado em branco** sobre a tarja preta saiu comido pela metade — preto invadindo branco num campo sem relação com o SVG (sintoma em dois elementos independentes ⇒ impressora; sintoma isolado ⇒ desenho daquele elemento). **Correção medida:** Argox OS-2140 PPLA, escala 0–20 — **10 (padrão de fábrica) não lê, 6 lê**. ⚠️ **A pegadinha vem antes do slider:** a caixa *"Usar configuração atual de intensidade da impressora"* vem marcada e deixa o slider **cinza** (o driver usa o valor do firmware); e o ajuste fica em *Preferências de impressão* → aba **Opções**, **não** em "Propriedades da impressora", que é outra janela. Ler o estado real do driver: `Get-PrintConfiguration -PrinterName "..."` (o XML do Seagull mostra o slider como `DisplayHint: Disabled`); abrir a janela: `rundll32 printui.dll,PrintUIEntry /e /n "<impressora>"`. ⛔ **Isso não tem correção por código:** a intensidade mora no DEVMODE privado do driver e nenhuma API web alcança (WebUSB também não — no Windows a impressora está capturada pelo driver de classe de impressora), e compensar no desenho é impossível nesta resolução — a 203 dpi o módulo tem **2,12 dots** e a impressora só liga/desliga dots inteiros. Do engrossamento medido, ~0,9 dot é fração de dot e **~1,8 dot é calor**. Por isso virou **aviso na tela** (`AvisoIntensidadeImpressora.tsx`, no popup do Testar Impressão) + `AjudaDaTela`. ⏭️ Módulo em **dots inteiros** fica para depois e exige parâmetro novo de resolução (203/300 dpi); numa etiqueta de 34 mm a 203 dpi, **2 dots é a única opção** (3 dots dariam 42,4 mm) — é por isso que temos menos folga que o legado, cujo módulo é 0,31 mm.
- **⚠️ Impressora de ETIQUETA não imprime folha — uma página por FILEIRA (2026-08-21):** mídia *die-cut* tem sensor de gap e alinha o papel no início de **cada página**; `@page` = largura × **passo do rolo**, com `break-after: page` entre fileiras. Assim o erro de passo não tem onde acumular. Mandar a folha longa entrega a origem vertical ao driver, que a fatia no tamanho do papel dele. ⚠️ Para paginar no navegador é preciso vencer duas regras que escondem trabalho **em silêncio**: `visibility: hidden` (o isolamento global de impressão deste projeto) esconde o pixel mas **mantém o espaço**, e `overflow: hidden` (`html, body, #root`, o shell de altura travada) **corta** o que passa da primeira página em vez de paginar — saía 1 página e as outras 19 sumiam sem aviso. Prenda a correção a uma classe no `<html>` **e** no `<body>`, senão ela apaga o `#root` de toda impressão do produto.
- **CPF/CNPJ validation:** CPF is always 11 numeric digits (unchanged). CNPJ is **alphanumeric** since Receita Federal's IN RFB 2.229/2024 (rollout from July 2026): positions 1–12 (raiz+ordem) accept `0-9A-Z`, positions 13–14 (check digits) are always numeric. Check-digit algorithm: each character's value = ASCII code minus 48 (digits keep 0–9, letters become 17–42); same weights/mod-11 as before (`[5,4,3,2,9,8,7,6,5,4,3,2]` then `[6,5,4,3,2,9,8,7,6,5,4,3,2]`). **Any table with a CNPJ field must reuse this logic** — see `web/src/lib/masks.ts` (`somenteAlfanumerico`, `cnpjValido`) and `api/.../cadastros/cliente/Documentos.java` for the reference implementation; never strip letters with a digits-only cleaner before validating/persisting a CNPJ.
- **⛔ Código de barras na faixa do gerador derruba a importação de estoque inteira (2026-08-20):** `EAN_CODIGO_BARRAS` começando por um prefixo reservado (hoje **`9`**, o do `gerar_ean13_interno()`) faz `EstoqueImportador` recusar **a planilha toda**, listando as linhas ofensoras — não importa metade. Motivo: quem migra de outro sistema traz códigos **já impressos nas etiquetas**, e um deles na nossa faixa colide com um SKU que o gerador **ainda vai emitir** (o sequencial cresce — o conflito nasce meses depois, numa bipada que traz o produto errado no caixa). Sai barato porque a importação é uma transação só e a tela tem o passo **Validar** antes do Importar. ⚠️ **O prefixo é DADO, não literal:** `cfg_ean_gerador.prefixo` (o gerador usa) + `prefixos_reservados` (a importação barra), com CHECK garantindo que o corrente esteja reservado — os SKUs já emitidos continuam com o prefixo antigo, então ele nunca pode ser liberado. Trocar é `UPDATE`, sem deploy. Duas armadilhas medidas ao escrever isto: `query(String[].class)` **não** lê array do Postgres (o driver devolve `PgArray` — tem de passar pelo `ResultSet`), e `prefixos_reservados || '8'` sem `::text` estoura com *"malformed array literal"*.
- **Código de barras interno do SKU (2026-07-22) — ⚠️ aviso para o Evirson:** `produto_barra.sku` **nunca** é texto livre digitado pelo usuário — é **sempre** gerado pela função SQL `gerar_ean13_interno()` (criada em `db/migration/V017__catalogo.sql`), que já existe e está testada (`api/src/test/java/com/vetor/niner/EanGeradorTest.java`, 2/2 verde). Formato `FIIISSSSSSSSD` (F=9 fixo, III=`id_banco` — a **instância** de banco, não o tenant —, SSSSSSSS=sequencial global de 8 dígitos, D=dígito verificador EAN-13/GTIN padrão). - **⚠️ Fuso: da LOJA no plano do lojista, da VETOR no plano da plataforma — e há um teste que reprova o build (2026-08-20):** o fuso do lojista vem da **UF da empresa** (`comum.tempo.FusoDaUf`, 27 entradas, identificador IANA nunca offset); o do plano de controle é fixo em `America/Sao_Paulo` (`comum.tempo.FusoDaPlataforma`), porque competência de cota, agenda de backup e vigência de assinatura são fatos do negócio da Vetor (P9) e um tenant com empresas em UFs diferentes não teria fuso para desempatar. **Decisão do dono do produto: por UF, sem exceção por município** — Fernando de Noronha (UTC−2, mas é PE) e o extremo oeste do AM (UTC−5, mas é AM) ficam com 1 h de desencontro **conhecido e aceito**, registrado no javadoc; não "consertar". ⚠️ **Formatar data também é comparação:** o driver devolve `timestamptz` como `OffsetDateTime` em **UTC**, então `FMT.format(doc.dataAutorizacao())` imprimia 3 h a mais — nenhum `DateTimeFormatter` do backend recebe `OffsetDateTime` sem passar por `FusoDaLoja`. - **⚠️ Date comparison always converts to the store's timezone, never the database's (2026-08-19):** the Postgres session runs in `Etc/UTC`, so a bare `CURRENT_DATE`/`now()` rolls over to the **next day at 21:00 Brasília**. Comparing `coluna_timestamptz::date` directly was therefore comparing against the *database's* day, not the store's — and it bit hard: at 21:30 the PDV answered *"Não há caixa aberto hoje"* with the morning's caixa still open, and `HorarioAcessoService` looked up the **wrong weekday** (`EXTRACT(ISODOW FROM now())` in UTC makes Friday 21:00 into "Saturday"), locking out users with a time window. Every comparison/grouping by date must be written `(coluna AT TIME ZONE 'America/Sao_Paulo')::date`, and every "today" `(now() AT TIME ZONE 'America/Sao_Paulo')::date` — **on both sides**, converting only one is still wrong. Columns that are genuinely `date` (`cliente.data_nascimento`, `conta_corrente.data_abertura`) are excluded: `AT TIME ZONE` on a `date` is meaningless. Storage is unaffected (`timestamptz` keeps storing the instant in UTC — this is a *read* convention). Swept across ~19 services on 2026-08-19; the details are in `docs/PROGRESSO.md`.
- **Tenant isolation — explicit `id_tenant` filter in every domain query, not just RLS (P8, hardened 2026-08-08):** a reproducible test (`CorGradeTamanhoCrudTest.isolamentoEntreTenants`) proved that a SELECT/UPDATE/DELETE relying *only* on the Postgres RLS policy — no `id_tenant = plataforma.tenant_atual()` written directly in the SQL text — can leak or modify another tenant's row; this also reproduced against old, previously-trusted, untouched code (`CategoriaProdutoService`). Root cause not fully diagnosed (suspected Postgres/JDBC generic-plan-caching interaction with the RLS qual across sessions with different `app.id_tenant`), but 100% fixed by defense-in-depth: **every `listar()`/`buscar()`/`atualizar()`/`excluir()` must filter `id_tenant` explicitly in the SQL** — `WHERE x.id_tenant = plataforma.tenant_atual() AND ...`, including inside `EXISTS`/`IN` dependency checks, cross-table `JOIN ... ON` clauses (`t1.id_tenant = t2.id_tenant`), and PK lookups sourced from JWT claims (e.g. `EuController` resolving `usuario`/`empresa` by id). `INSERT`s are unaffected (they already write `plataforma.tenant_atual()` directly). Full writeup, the exact fix pattern, and the list of files touched in the audit: `docs/infra/isolamento-tenant-rls.md`. Any new service must be written with this filter from the start — it is not an optional hardening pass.
- **Desfazer dinheiro nunca toca caixa fechado em silêncio (2026-08-14):** qualquer rotina que apague ou altere um lançamento de `caixa_detalhe` já existente **tem que chamar `CaixaService.exigirCaixaAbertoParaDesfazer(VinculoCaixa.X, id)` antes** — nunca `DELETE FROM caixa_detalhe` direto. - **Vínculo sem FK cobra atenção no `excluir()` (2026-08-14):** várias colunas de ligação do financeiro (`caixa_detalhe.id_conta_pagar`, `conta_corrente_movimento.id_conta_pagar`, `caixa_detalhe.id_lote_recebimento`) foram criadas **sem FK, de propósito** — o que significa que **o banco não reclama quando um DELETE esquece o outro lado**. Foi assim que `ContaPagarService.excluir()` passou meses deixando o movimento de caixa/banco órfão. Ao escrever ou revisar um `excluir()`, pergunte *"que outras tabelas esta operação escreveu quando criou o registro?"* e apague todas; desconfie especialmente quando existir um método privado que já faz esse DELETE (padrão "apaga e regrava") e só o caminho de POST/PUT o chama. - **Efeito secundário não roda dentro da transação principal (2026-08-18):** medição, log de negócio e qualquer gravação "de apoio" ficam **fora** da transação que cria o registro principal. O motivo é específico do Postgres e traiçoeiro: quando um comando falha, **a transação inteira é abortada**, e capturar a exceção em Java **não desfaz isso** — o `COMMIT` seguinte é tratado como `ROLLBACK` e **devolve sucesso**. Foi assim que o signup passou a responder **201 com token válido e a conta inexistente** (bug real desta data, ao ligar o funil de aquisição em `SignupService`). `try/catch` não protege; `@Transactional(REQUIRES_NEW)` também não resolve sozinho quando há FK para a linha ainda não commitada (`lead.id_tenant → tenant` falhava). A saída é chamar **depois do commit** — no controller, como faz `OnboardingController.assinar` → `AquisicaoService.converter`. Teste de regressão: `AquisicaoFunilTest.signupSobreviveAFalhaDeMedicao`, que **confere a conta depois do 201**, não só o status.
- **`@Transactional` não vale em auto-invocação — vale dobrado em worker (2026-08-18):** método anotado chamado de dentro do próprio bean (`this.pegarLote()`) não passa pelo proxy do Spring e roda **sem transação**. Num consumidor de fila isso é silencioso e grave: o `FOR UPDATE SKIP LOCKED` solta o lock no fim do statement e dois workers pegam o mesmo evento. Padrão do projeto: **agendador em um bean, trabalho transacional em outro** — ver `CobrancaWebhookJob` (só `@Scheduled`) × `CobrancaWebhookProcessador` (`@Transactional`).

- **Duas populações de usuário, dois decoders (2026-08-19, R18/ADR-009):** `/api/v1` aceita **só** `aud=tenant` e `/api/admin` **só** `aud=plataforma` — são dois beans `JwtDecoder` (`jwtDecoder` e `jwtDecoderStaff`), não um permissivo. ⚠️ **O `@Qualifier("jwtDecoderStaff")` na cadeia de admin é obrigatório:** com dois candidatos do mesmo tipo, o `@Primary` (o de tenant) vence a resolução por nome do parâmetro, e sem ele o Spring injeta o decoder errado **em silêncio** — token de lojista abre o backoffice. Um evento que chegasse à fila viraria dead-letter com *"nenhum manipulador registrado"*. ⛔ **O sintoma engana:** o painel mostrando *"0 pendentes, 0 erros"* parece saúde e é **ausência de trabalho**. Vale para qualquer fila, agendador ou gatilho: `grep` por quem **publica** e por quem **consome** antes de afirmar que o mecanismo está no ar.

Mexem em estoque **oito rotinas** — PDV, transferência, devolução ao fornecedor, devolução de venda, **cancelamento de entrada** (de que ninguém lembra), cancelamento de devolução, balanço e importação — mais o que vier. Espalhar a checagem por serviço garante **matematicamente** que uma fique de fora, e a que ficar de fora falha **em silêncio**. `produto_estoque` é onde o saldo realmente mora, qualquer que seja o caminho. ⚠️ **Mas o gatilho só decide o que não envolve cálculo:** quando há regra de dinheiro (arredondamento, HALF_UP, arredonda-uma-vez-no-fim), o gatilho no máximo **avisa** e o **Java** calcula — reescrever a mesma regra em plpgsql cria duas implementações que divergem no dia em que só uma for corrigida (P7). ⚠️ E o caminho comum não pode pagar por isso: uma saída antecipada barata (`saldo >= 0`, um `EXISTS` indexado) vem antes de qualquer leitura de configuração, senão uma importação de 10 mil linhas paga a conta. *(O mesmo desenho serviu ao gatilho de sincronização de marketplace, V067, removido em 2026-08-28 junto com a integração.)*
